# Next 웹 서버에서 파일을 전사한다

`apps/web`은 브라우저에서 선택한 음성·영상 파일 한 개를 받아 `large-v3`로 전사하는 Next 앱이다. 파일 선택, 업로드 진행, SSE로 받는 상태·중간 전사, 취소, 결과 복사와 텍스트 다운로드를 제공한다. SSE는 서버가 열린 HTTP 응답으로 이벤트를 보내는 방식이며, 브라우저는 전사가 끝나기 전에 완성된 구간부터 표시한다. CLI와 같은 공유 전사 실행기를 사용하며 전사 전체는 별도 Node 프로세스에서 실행한다. 운영자가 승인한 화면과 세 애니메이션은 운영 서버에 반영하고 검증했다. 구조·자료 수명·전송 방식 비교·개발 및 운영 검증 근거는 영구 문서인 [전사 아키텍처 인수인계](전사-아키텍처-인수인계.md)에 보존했다.

## 1. 실행 환경을 준비한다

저장소 최상위에서 실행한다.

```bash
node --version
pnpm --version
pnpm install --frozen-lockfile
```

| 항목 | 지정한 버전 | 역할 |
|---|---|---|
| Node.js | `^20.16.0 \|\| >=22.3.0` | 웹·전사 프로세스를 실행한다. 공유 원본 모듈을 읽는 `process.getBuiltinModule()` 때문에 이 범위를 사용한다. |
| pnpm | `12.5.1` | CLI·웹·공유 패키지의 의존성과 명령을 관리한다. |
| Next | `16.3.8` | App Router와 개발·운영 HTTP 서버를 제공한다. |
| React·React DOM | `19.3.0` | 파일 선택·진행·결과 화면을 렌더링한다. |
| `server-only` | `0.0.1` | 서버 전용 전사 모듈을 브라우저 코드에서 가져오면 빌드를 실패시킨다. |

실행 검증 환경은 macOS·Apple Silicon·Node `24.18.0`·pnpm `12.5.1`이다. 지정한 Node `20.16.0`과 `22.3.0`의 HTTP 진단 채널 존재는 공식 소스에서 확인했으며, 두 버전에서 앱을 실행한 검증은 하지 않았다. 설치·모델 문서의 개별 도구 설명과 함께 이 문서의 저장소 실행 범위도 적용한다.

웹 서버 시작과 `GET /api/health`에는 모델·FFmpeg·전사 엔진이 필요하지 않다. 실제 전사에는 준비된 엔진과 모델이 필요하므로 [위스퍼 대형 모델 업그레이드](위스퍼-대형-모델-업그레이드.md)의 설치·빌드·모델 준비 절차를 먼저 따른다. 웹은 모델을 `large-v3`로 지정하며 CLI의 모델 환경 변수는 웹 모델 선택에 사용하지 않는다.

## 2. 개발 또는 운영 서버를 실행한다

다음 예시는 `3998` 포트다. 이미 사용 중이면 빈 포트를 골라 명령과 접속 주소에 같은 값을 쓴다. `PORT`를 생략하면 Next 기본 포트인 `3000`을 사용한다.

```bash
# 개발 서버
PORT=3998 pnpm dev
```

운영 서버는 현재 소스를 빌드한 뒤 실행한다. 개발 서버와 같은 포트를 쓰려면 해당 개발 서버를 먼저 종료한다.

```bash
pnpm build
PORT=3998 pnpm web:start
```

| 루트 명령 | 실행 대상 | 쓰는 때 |
|---|---|---|
| `pnpm dev` | `apps/web/scripts/dev.mjs` → Next 개발 CLI | 웹 소스의 자동 갱신이 필요한 개발 중에 쓴다. |
| `pnpm build` | `next build` | 현재 소스의 운영 빌드를 만든다. |
| `pnpm web:start` | `next start --hostname 0.0.0.0` | 만들어 둔 운영 빌드를 실행한다. |
| `pnpm start`, `pnpm convert` | `apps/cli/src/index.js` | 기존 CLI 전사를 실행한다. |
| `pnpm lint` | 루트 ESLint, 경고도 실패 | 웹·CLI·공유 코드와 설정을 검사한다. |
| `pnpm test` | 검사 명령이 있는 작업 공간 패키지 | 공유·프로세스 28개, CLI 15개, 웹 57개, 총 100개 검사를 실행한다. |
| `pnpm --filter @stt/web test` | Node 웹 검사 | 접수·결과·취소·정리와 구간 추출·SSE·브라우저 수신 경계를 검사한다. |

`.next`는 Git에서 제외한 빌드 생성물이다. 소스를 바꾼 뒤에는 다시 빌드해야 운영 서버에 반영된다. Next 빌드와 ESLint는 별도 명령으로 확인한다.

Windows PowerShell의 포트 지정 문법은 다음과 같다.

```powershell
$env:PORT = '3998'
pnpm dev
```

개발·운영 명령은 모두 `0.0.0.0`에서 수신한다. 같은 기기는 `http://127.0.0.1:3998/`, 같은 네트워크의 다른 기기는 `http://<서버의 네트워크 주소>:3998/`에 접속한다. 예를 들어 서버 주소가 `10.1.1.100`이면 `http://10.1.1.100:3998/`이다. 기기의 방화벽이나 네트워크의 기기 간 통신 설정에 따라 다른 기기에서 연결되지 않을 수 있으므로 서버 주소의 상태 확인 응답을 먼저 확인한다.

```bash
curl --fail --include http://127.0.0.1:3998/api/health
```

기대 결과는 HTTP `200`과 `{"status":"ok"}`다. 이 경로는 모델을 준비하거나 전사하지 않는다. 서버를 실행한 터미널의 Ctrl+C는 그 서버의 현재 작업을 취소하고 정리한 뒤 종료한다.

## 3. 파일을 선택하고 진행 상태를 확인한다

1. 웹 페이지에서 「파일 선택」을 누른다. `.mp3`, `.wav`, `.m4a`, `.flac`, `.ogg`, `.mp4`, `.avi`, `.mov` 중 한 파일을 선택한다. 대소문자는 구분하지 않는다.
2. 파일 이름과 크기를 확인하고 「전사 시작」을 누른다. 빈 파일이나 `512MiB`를 넘는 파일은 시작할 수 없으며 이유를 표시한다.
3. 업로드 중 실제 전송 바이트·전체 크기·진행률·경과 시간을 확인한다. 서버 접수가 끝나면 같은 작업의 SSE에 연결해 상태와 중간 전사를 받는다. 전사 상태를 1초마다 조회하지 않는다.
4. 첫 구간을 받으면 「중간 전사 결과」에 표시하고 새 구간을 이어 붙인다. 연결이 잠시 끊기면 받은 부분을 유지하며 자동으로 복구한다. 화면을 갱신할 때 읽던 위치를 강제로 맨 아래로 옮기지 않는다.
5. 성공과 정리가 끝나면 서버에 저장한 최종 파일을 읽어 전체 결과로 바꾼다. 결과를 복사하거나 `.txt` 파일로 내려받는다. 「다음 파일 선택」은 화면의 이전 작업을 지우고 새 입력 화면으로 돌아간다. 이전 성공 텍스트 파일은 서버에 남는다.

| 구간 | 화면의 피드백 | 값의 의미 |
|---|---|---|
| 파일 선택 창·선택 반영 대기 | 「파일 선택 반영을 기다리고 있습니다」 안내, 전사 시작 비활성 | 큰 파일이 브라우저 입력에 반영되는 동안 표시한다. 선택 완료나 창 취소로 해제한다. |
| 파일 전송 | 진행 막대·실제 바이트·백분율·경과 시간·「업로드 취소」 | 단일 XHR 요청의 업로드 이벤트에서 받은 전송량이다. 파일 전체를 JavaScript 메모리로 읽지 않는다. |
| 파일 전송 100% | 「파일 전송이 끝났습니다. 서버의 저장·접수를 기다리고 있습니다」 | 전송 완료와 서버의 `202` 접수를 구분한다. 이때도 접수 응답을 받기 전까지 업로드 취소가 가능하다. |
| 모델·입력 준비 | 준비 상태·중앙 SVG 애니메이션·경과 시간·「전사 취소」 | 서버가 공유 실행기를 호출해 모델과 입력을 준비한다. |
| 음성 전사 | 전사 상태·중앙 SVG 애니메이션·경과 시간·취소·중간 텍스트 | 엔진이 출력한 시간 구간을 표시한다. 구간 도착을 전사 완료 백분율로 바꾸지 않는다. |
| SSE 재연결 | 재연결 안내·이미 받은 부분 유지 | 브라우저가 같은 작업에 다시 연결하고 누락 이벤트 또는 누적 상태를 받는다. 전사를 새로 접수하지 않는다. |
| 취소·작업 정리 | 정리 중 안내 | 자손 프로세스·잠금·임시 파일·업로드 사본을 정리한다. 실제 완료 전에는 취소 완료나 전사 성공을 표시하지 않는다. |
| 성공 | 최종 파일 확인 뒤 전체 결과 | 실패 배열이나 빈 파일은 성공으로 표시하지 않는다. 최종 파일을 못 읽으면 받은 부분을 유지하고 같은 작업 재시도를 안내한다. |
| 실패·취소 | 「미완료 전사 결과」와 종료 전 부분 텍스트 | 받은 부분은 복사할 수 있지만 최종 파일 다운로드는 제공하지 않는다. |

한 Next 서버에서 업로드·전사·정리를 포함해 한 작업만 처리한다. 실행 중 다른 접수는 `409`로 안내하며 대기열이나 자동 접수 재시도는 없다.

음성 파형·구간 이어 붙이기·소리의 잔향 애니메이션 중 하나를 새 작업의 UUID로 정한다. 선택 메뉴는 없으며 같은 작업을 재연결·조회·새로고침하면 같은 종류를 유지한다. 무작위로 정하므로 연속 작업에서 같은 종류가 나올 수 있다. `accepted`·`running`일 때만 결과 영역 위에 가운데 표시하며 성공·실패·취소 뒤에는 숨긴다. 정리 중에도 상태가 활성 상태이면 표시를 유지하고, 동작 줄이기 설정과 화면 읽기 안내를 제공한다.

업로드 취소는 전송 요청을 중단한다. 접수 뒤 취소는 작업 UUID의 취소 API에 요청한다. 취소 요청이 실패하면 같은 작업에서 다시 요청할 수 있다. 취소가 접수되면 같은 작업의 이벤트를 이어 받으며 실제 정리 완료를 기다린다. 페이지 이동·탭 닫기·SSE 연결 중단은 구독만 해제하며 작업을 취소하지 않는다.

## 4. 결과를 사용하고 같은 작업을 다시 조회한다

중간 전사와 성공 결과는 읽기 전용 텍스트 영역에 표시한다. 성공 이벤트를 받으면 `resultUrl`의 최종 텍스트 파일을 GET으로 읽고 표시를 교체한다. 중간 구간을 단순히 이어 붙인 값을 최종 파일로 취급하지 않는다. 「부분 결과 복사」 또는 「결과 복사」를 사용할 수 없는 네트워크 HTTP 주소나 브라우저에서는 이유를 안내한다. 「텍스트 선택」으로 결과를 선택해 기기의 복사 명령을 사용하거나 성공한 작업의 「텍스트 다운로드」로 받는다. 다운로드 이름은 원래 파일의 기본 이름에 `.txt`를 붙인다.

작업 접수 뒤 페이지 주소에 `?job=<UUID>`를 남긴다. 같은 서버가 실행 중이면 새로고침하거나 그 주소를 열어 해당 작업의 SSE에 연결한다. 처음에는 누적 구간과 현재 상태를 받고 이후 새 이벤트를 받는다. 자동 재연결은 `Last-Event-ID`로 마지막 순번 뒤의 이벤트를 요청하며 화면은 같은 순번을 다시 반영하지 않는다.

연결이 복구 가능한 상태이면 브라우저의 `EventSource`가 재연결한다. 완전히 닫힌 연결은 상태 GET으로 한 번 진단하며 반복 조회하지 않는다. 「같은 작업 다시 조회」는 같은 UUID에 새 SSE 구독을 만들고, 성공한 작업이면 최종 파일도 다시 읽는다. 조회 오류·없는 작업 `404`·결과 읽기 실패 모두 새 업로드나 전사를 자동으로 만들지 않는다.

중간 텍스트는 한 작업당 UTF-8 16MiB까지 보관한다. 이 상한을 넘으면 `streamNotice`로 안내하고 새 중간 구간 보관을 멈추지만 전체 전사와 최종 파일 저장은 계속한다. 안내가 있으면 성공 후 최종 파일에서 전체 결과를 확인한다.

작업 상태는 단일 Next Node 프로세스의 메모리에 있다. 서버 재시작 뒤 이전 UUID의 조회는 `404`가 되며 자동으로 다시 전사하지 않는다. 성공 텍스트는 디스크에 남아 있으므로 서버 파일에서 확인할 수 있다. 작업 이력 저장과 여러 서버 인스턴스 운영은 이번 구성에 포함하지 않는다.

| 자료 | 위치 | 수명 |
|---|---|---|
| 업로드 사본 | `assets/web-jobs/<UUID>/input.<확장자>` | 접수 실패·성공·실패·취소 후 정상 정리하면 삭제한다. 브라우저 원본은 변경하지 않는다. |
| 성공 텍스트 | `output/web-jobs/<UUID>/input.txt` | 전사 성공 뒤 보존한다. 서버 재시작에도 파일은 남는다. |
| 실패·취소 출력 | 같은 작업의 `output/web-jobs/<UUID>/` | 정상 정리하면 삭제한다. 기존 CLI 결과는 변경하지 않는다. |
| 작업 상태 | 서버 작업 관리자의 메모리 | 서버 수명 동안 조회할 수 있다. 개발 HTTP 모듈들이 같은 관리자를 참조한다. |
| 누적 중간 구간·최근 이벤트 | 같은 작업의 서버 메모리 | 중간 텍스트 16MiB와 최근 이벤트 1000개를 보관한다. 재시작하면 사라지며 성공 파일과 수명이 다르다. |
| 정리 실패 자료 | 해당 작업의 업로드·출력·잠금 | `cleanupRequired: true`로 새 접수를 막는다. 운영자가 자손 종료와 남은 자료를 확인해야 한다. |

두 `web-jobs` 폴더는 Git에서 제외한다. 정리 실패 상태를 자동으로 풀어 주는 API는 없다. 실행 중인 자손이 남았는지 확인하지 않고 업로드나 잠금을 삭제하면 같은 자료를 사용 중인 프로세스와 충돌할 수 있다.

## 5. HTTP 경로와 오류를 확인한다

파일 이름은 URL 인코딩한 `name` 질의 값으로, 내용은 `application/octet-stream` 바이너리 본문으로 보낸다. 이름의 빈 값·경로 구분자·제어 문자를 거절하며 실제 저장 경로에는 원래 이름을 사용하지 않는다. `<UUID>`는 접수 응답의 작업 식별자다.

| 경로 | 역할 | 응답 |
|---|---|---|
| `POST /api/transcriptions?name=<파일 이름>` | 한 파일 저장·접수 | `202` 작업 정보. 입력 오류 `400`, 형식 오류 `415`, 크기 초과 `413`, 실행 중 `409`, 종료 중 `503`. |
| `GET /api/transcriptions/<UUID>` | 상태·단계·오류·결과 주소 조회 | `200` 작업 정보. 잘못된 UUID `400`, 없는 작업 `404`. |
| `GET /api/transcriptions/<UUID>/events` | 상태·중간 구간·종료 SSE 구독 | `200` UTF-8 `text/event-stream`, 잘못된 UUID `400`, 없는 작업 `404`, 종료 중 `503`. |
| `POST /api/transcriptions/<UUID>/cancel` | 전사 취소·정리 요청 | 처리 중 `202`, 이미 끝난 작업은 기존 상태와 `200`. |
| `GET /api/transcriptions/<UUID>/result` | 성공 텍스트 다운로드 | `200` UTF-8 `text/plain`. 성공 전·실패·취소 `409`, 없는 작업 `404`, 결과 읽기 실패 `500`. |
| `GET /api/health` | HTTP 서버 응답 확인 | `200`, `{"status":"ok"}`. |

작업 응답에는 `id`, `name`, `size`, `model`, `status`, `stage`, `createdAt`, `updatedAt`, `statusUrl`, `cancelUrl`, `eventsUrl`, `resultUrl`, `error`, `cleanupRequired`, `streamNotice`가 있다. `eventsUrl`은 같은 작업의 SSE 주소이고, `streamNotice`는 중간 텍스트 보관 상한 안내 또는 `null`이다. 상태는 `accepted`, `running`, `succeeded`, `failed`, `cancelled`, 단계는 `preparing`, `transcribing`, `cleaning`, `complete`다. 오류는 `{ "error": { "code": "...", "message": "..." } }`로 안내하며 서버 경로와 원시 엔진 로그는 보내지 않는다. 상태·결과·이벤트 응답은 `Cache-Control: no-store`를 사용한다.

| 이벤트 | 공개 데이터 | 받는 쪽의 동작 |
|---|---|---|
| `snapshot` | `{ job, segments, seq }` | 누적 구간과 현재 작업으로 화면을 교체한다. |
| `state` | `{ job, seq }` | 작업 상태·단계·오류를 반영한다. |
| `segment` | `{ jobId, seq, startMs, endMs, text }` | 해당 작업의 새 구간을 추가한다. 시간은 밀리초다. |
| `terminal` | `{ job, seq }` | 정리를 마친 종료 상태를 반영하고 구독을 닫는다. 성공이면 최종 파일을 읽는다. |

SSE `id`는 이벤트의 `seq`와 같다. 유효한 `Last-Event-ID`가 최근 1000개 기록 범위에 있으면 그 뒤 이벤트만 다시 보낸다. 순번이 없거나 잘못됐거나 범위 밖이면 스냅샷으로 복구한다. 재전송 프레임 합계가 1MiB를 넘는 경우에도 큰 초기 스냅샷 한 번으로 대체한다. 이후 구독의 전송 대기는 1MiB까지 허용하고 초과한 연결만 닫는다. 초기 스냅샷은 이 대기 상한의 예외다. 이미 끝난 작업은 현재 순번의 스냅샷과 종료 이벤트를 보내며 둘의 순번이 같을 수 있다. 연결 유지 주석은 15초 간격이고 새로운 이벤트 순번을 만들지 않는다.

터미널에서 SSE를 직접 확인하려면 다음 주소의 `<UUID>`를 실제 `202` 접수 응답의 `id`로 바꾼다. 주소는 큰따옴표로 감싸며 `--no-buffer`는 구간 도착 즉시 출력을 표시하도록 curl의 출력 버퍼를 끈다. 없는 작업이면 `404`, 종료 중이면 `503`으로 실패하며 이 요청은 전사를 시작하지 않는다.

```bash
curl --no-buffer --fail --include "http://127.0.0.1:3998/api/transcriptions/<UUID>/events"
```

상한은 정확히 `536870912`바이트다. `Content-Length`가 이를 넘으면 저장 전 거절한다. 길이 헤더 없이 실제 입력이 상한을 넘으면 그 조각부터 디스크 쓰기를 중단하고 남은 입력을 버린 뒤 요청이 끝나면 `413`을 반환한다. 입력 전체를 메모리에 모으지 않으며 그동안 슬롯을 유지한다.

## 6. 서버 실행·모듈·종료 경계를 이해한다

`src/server/transcription.js`는 `server-only`와 Node의 `createRequire()`를 사용해 공유 공개 실행기를 원본 CommonJS 파일에서 가져온다. `runTranscription()`이 전사 전체를 자식 프로세스에 맡기므로 Next의 작업 폴더와 HTTP 응답을 유지한다. 공유 패키지의 `src`를 수정하면 Node 모듈 캐시를 새로 읽도록 개발 서버를 다시 실행한다.

`src/server/transcription-jobs.js`는 `globalThis`의 공통 식별자에 작업 관리자를 보관한다. 접수·조회·취소·결과·SSE 경로와 Node instrumentation이 이 관리자를 사용한다. POST는 첫 비동기 처리 전에 슬롯과 공식 `after()` 완료 흐름을 등록하므로 업로드 중 종료도 정리 대상으로 추적한다. SSE 연결은 이미 접수한 작업을 구독하며 전사 실행을 시작하지 않는다.

공유 실행기의 `onLog`가 UTF-8 표준 출력을 전달하면 `segment-parser.js`가 완성된 `[시작 시간 --> 끝 시간] 텍스트` 줄을 해석한다. `job-events.js`가 상태와 구간에 순번을 붙이고 `event-stream.js`가 HTTP 이벤트로 보낸다. 미완성 줄은 64KiB까지 보관한다. 시간과 문장이 같은 엔진 원출력도 각 구간을 보존하며, 라이브러리가 종료 때 `Stdout:` 표식으로 전체 출력을 다시 내보내는 블록은 제외한다. 표준 오류와 일반 엔진 안내는 화면 구간으로 보내지 않는다.

개발 종료 대기는 `apps/web/.env.development`의 `NEXT_EXIT_TIMEOUT_MS=10000`이다. `scripts/dev.mjs`가 Node의 `loadEnvFile()`로 개발 부모에서 값을 읽은 뒤 Next CLI를 실행한다. 설치된 Next 개발 CLI의 기본 자식 종료 대기는 100ms라 전사 정리가 끝나기 전에 강제 종료될 수 있어 이 값을 적용했다. Node `--env-file` 옵션을 직접 쓰면 Next가 해당 옵션을 `NODE_OPTIONS`로 전달해 시작에 실패했으므로 사용하지 않는다.

웹 신호 처리기는 SIGINT·SIGTERM에서 열린 SSE HTTP 응답을 먼저 닫고 관리자를 종료 상태로 바꾼 뒤 현재 작업에 중단 신호를 전달한다. 직접 `process.exit()`를 호출하지 않으며 Next의 `after`가 전사·파일 정리를 기다린다. 미완료 업로드 취소에서는 파일 닫기와 부분 파일 삭제를 먼저 기다린 뒤 `Connection: close` 응답을 반환한다. Node HTTP 입력의 `body.cancel()` 반환 Promise가 끝나지 않는 실제 경계를 확인했으므로 그 Promise를 종료 완료 근거로 기다리지 않는다.

SSE 구독의 읽기 큐 종료와 실제 HTTP 쓰기 종료는 다르다. 설치된 Next는 `ServerResponse.write()`에 역압력이 생기면 `drain`을 기다리며, 현재 쓰기가 대기 중이면 `ReadableStream.error()`만으로 소켓을 닫지 못한다. `event-responses.js`가 공개 `node:diagnostics_channel`의 `http.server.request.start`에서 SSE GET의 실제 `ServerResponse`만 추적하고 SIGINT·SIGTERM 때 `destroy()`한다. 평상시 응답의 `finish`·`close`에는 추적과 자신의 리스너를 해제한다. 종료 시 채널 구독도 해제하므로 후속 신규 구독의 `503` 응답을 가로채지 않는다. 일반 HTTP 응답을 일괄 종료하거나 Next의 비공개 종료 함수를 호출하지 않는다.

HTTP 진단 채널은 공식 문서상 실험 기능이다. Node·Next를 올릴 때 채널의 발행 정보와 등록 시점, 느린 완료 스냅샷의 실제 소켓 종료를 다시 확인해야 한다. 지정한 최소 버전의 채널 생성·발행은 [Node 20.16.0 공식 소스](https://raw.githubusercontent.com/nodejs/node/v20.16.0/lib/_http_server.js)와 [Node 22.3.0 공식 소스](https://raw.githubusercontent.com/nodejs/node/v22.3.0/lib/_http_server.js)에서 확인했다. 실험 기능 표기는 [Node 진단 채널 문서](https://nodejs.org/api/diagnostics_channel.html#built-in-channels), 연결된 소켓까지 닫는 동작은 [HTTP 응답 종료 문서](https://nodejs.org/api/http.html#outgoingmessagedestroyerror)에 있다.

개발 화면은 localhost·127.0.0.1·서버의 실제 네트워크 주소를 `allowedDevOrigins`에 넣는다. `0.0.0.0` 수신 중 127.0.0.1의 개발 갱신 요청이 차단되었던 문제를 해결한다. 운영 실행은 전체 저장소·의존성·모델을 유지한 `next start`이며 `.next`만 복사하는 배포는 구성하지 않았다.

## 7. 오류 원인을 구분한다

| 관측 | 확인할 원인 | 처리 |
|---|---|---|
| `EADDRINUSE` | 지정 포트를 다른 서버가 쓰고 있다. | 그 서버를 유지하고 빈 포트를 지정한다. |
| 파일 선택 후 시작할 수 없다. | 빈 파일·미지원 확장자·크기 초과 또는 선택 반영 대기다. | 화면의 이름·크기·오류·대기 문구를 확인한다. 최대 512MiB 파일 한 개를 선택한다. |
| 업로드 100%에서 기다린다. | 파일 전송은 끝났지만 서버의 저장·접수 응답 전이다. | 접수 대기 문구와 경과 시간을 확인한다. 필요하면 업로드를 취소한다. |
| 다른 작업 실행 안내 `409` | 업로드·전사·정리 슬롯이 사용 중이다. | 진행 중인 작업의 정리가 끝난 뒤 직접 시작한다. |
| 모델·엔진 준비 실패 | 실제 large-v3 모델이나 실행 파일 준비가 끝나지 않았다. | [모델 업그레이드 문서](위스퍼-대형-모델-업그레이드.md)의 검증 절차를 따른다. |
| 정리 확인 필요 | 자손 종료 또는 파일 삭제를 완료하지 못했다. | 운영자가 해당 작업의 서버 로그·하위 프로세스·자료를 확인한다. 자동 재접수하지 않는다. |
| 이전 작업 `404` | UUID가 없거나 서버를 재시작했다. | 보존한 성공 텍스트의 서버 경로를 확인한다. 새 작업은 사용자가 직접 시작한다. |
| 중간 전사 연결이 끊겼다. | 일시적인 네트워크 단절 또는 서버 연결 종료다. | 자동 재연결 중에는 받은 부분을 유지한다. 복구되지 않으면 「같은 작업 다시 조회」로 같은 UUID의 구독을 다시 연다. |
| 성공했지만 최종 파일을 못 읽었다. | 결과 HTTP 요청 또는 서버 파일 읽기가 실패했다. | 받은 부분을 최종 결과로 표시하지 않고 같은 작업 재시도로 최종 파일을 다시 읽는다. |
| 중간 표시 보관 상한 안내 | 한 작업의 중간 텍스트가 UTF-8 16MiB 상한에 도달했다. | 전사 완료를 기다린 뒤 최종 파일에서 전체 결과를 확인한다. |
| 자동 복사 불가 | 접속 주소의 보안 조건이나 브라우저 권한이 제한한다. | 텍스트 선택·기기의 복사 명령 또는 다운로드를 사용한다. |
| `process.getBuiltinModule` 오류 | 지정한 Node 실행 범위보다 오래된 버전이다. | 20.16 이상의 20 계열 또는 22.3 이상으로 실행한다. |
| 공유 패키지를 찾지 못한다. | 의존성 또는 앱 기준 작업 폴더가 맞지 않는다. | 루트에서 고정 설치 후 제공한 pnpm 웹 명령으로 실행한다. |
| 이전 화면이 보인다. | 이전 운영 빌드를 실행하고 있다. | 현재 소스를 빌드한 뒤 해당 운영 서버를 다시 실행한다. |
